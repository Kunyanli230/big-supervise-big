# 关键决策点与高效分支设计

日期：2026-11-10。状态：机制分析与实验设计，尚未实现或运行。

## 1. 什么节点值得分支

关键性和分支价值是两个条件。提交补丁很关键，但不一定需要多分支；三个不同命令也可能只是实现同一个子目标。

一个值得分支的节点，需要同时满足：

1. 有至少两个未被已执行证据排除的具体方案。
2. 方案会改变后续根因判断、修改位置、行为契约或验证结论；差异不只是命令语法。
3. 选错会导致实质性的后续浪费、回滚或回归。
4. 额外计算有机会帮助区分方案，而且没有更便宜的共享检查能够先消除分歧。
5. 当前剩余预算允许得到有用证据。若短程验证做不到，记录待验证差异，不假装已经比较出了优劣。

不能用 Decisions 的选项概率直接解释为“分支带来的成功率增益”；它首先是选择读数，尚未校准为计算价值。

## 2. 节点类型及处理方式

| 节点 | 真正有意义的差异 | 默认处理 |
| --- | --- | --- |
| 初始定位 | 两条可信调用路径指向不同责任模块 | 先共享检索；有证据冲突后才比较两条路径 |
| 根因承诺 | 不同因果解释要求不同修改 | 优先做一个能区分假设的最小复现或只读探针 |
| 首次核心修改 | 修改生产者还是消费者、局部修复还是公共契约调整 | 若两方案均有证据支持且影响不同，优先分支 |
| 测试失败后的修订 | 实现错误、假设错误、测试环境问题 | 先读并分类错误；证据仍冲突时才分支 |
| 回归结果冲突 | 目标测试通过但相关路径失败 | 优先比较修复契约及回归原因 |
| 多次无进展 | 相同信息反复出现，且不是有进展的后台任务 | 触发重新诊断；只有找到具体替代假设才分支 |
| 测试选择 | 不同测试能区分不同根因或边界行为 | 通常选择一个信息量高的测试；不为运行命令形式分支 |
| 是否结束 | 已通过检查是否覆盖任务要求，是否存在未验证的具体风险 | 单次审查；有具体疑点时做针对性检查 |
| 常规读取、明确修改、格式化 | 一般没有实质方案分歧 | 单分支 |
| 测试轮询、查看 patch、提交 | 通常只是执行既定计划 | 单分支或确定性等待控制 |

“第一处修改”是审查候选节点，不是强制展开节点。清晰的一行修复没有必要生成三个版本。

## 3. 现有轨迹能支持什么结论

证据文件：`AB_轨迹诊断证据.json` 和 `典型轨迹片段.json`，均来自此前只读诊断，本次未重新访问 VM。

- 第 21 题 vuls 的摘录中，32 条命令涉及测试退出文件，其中第一条启动后台测试，之后 31 条显式检查状态。编译、链接仍有进展时，应视为等待控制问题，不应自动解释为根因探索陷入死胡同。
- 第 20 题 qutebrowser 的摘录显示定向测试已通过，后续查看补丁。这类动作通常适合单分支。是否应该结束仍需检查任务覆盖和未验证风险，不能因局部测试通过就自动断定修复正确。
- 相同动作可能附带不同可见思考，影响后续模型历史；因此“相同动作”不意味着整个未来轨迹严格等价。

## 4. 推荐方法：事件触发、探针优先、两路短程分支

这是对之前 B2 的细化。核心从“生成三个下一步动作”改为“比较有证据支持的两个子任务方案”。

### 4.1 先用程序事件缩小监督范围

候选事件包括：新复现结果、新失败类型、拟执行核心代码修改、目标测试与回归测试冲突、连续两次没有新证据或有效状态变化。

事件只是触发审查，不能直接等同于触发分支。后台进程仍在推进时，无新日志不算根因停滞。合法的重复测试也不能按字符串相同就禁止。

默认保持一条 Policy 轨迹。能从前一观察检测的事件，在下一次生成前判断；只有看到待执行动作才能发现的事件，例如首次写代码，则先生成一个动作，再在执行前判断，并复用该候选，不重新付费生成同样的第一候选。这是混合时机设计，并非所有门控都发生在首次生成前。

### 4.2 Decisions 只选择可实现的路线

固定路线菜单：

- CONTINUE：已有证据足够，继续单轨。
- PROBE：缺证据，先生成或选择一个区分性检查。
- COMPARE：存在两个具体、可检验的不同方案，进入比较。
- REPLAN：当前假设受挫，但尚无可用替代方案；先更新假设再考虑分支。
- WAIT：后台任务仍有进展，按程序规则等待或查询。

Decisions 接口不被假设为可自由生成任意计划。具体假设、测试及方案卡由 Policy 在事件节点提供，额外请求计费。固定对比模板可引导“当前解释”和“最可信替代解释”，但不能强造一个没有证据支持的反对方案。

每张方案卡至少包含：根因或方案、已观察证据、预期差异、可推翻它的结果、下一段子目标及预算。引用源码、已执行输出或任务要求；模型自我评价不是证据。

### 4.3 先寻找共享的区分性检查

例：重复记录究竟来自输入重复，还是重复调用写入过程？一个小型复现若能同时记录“输入数量、写入调用次数”，可能一次就排除一个解释。此时只跑这个探针，不需要复制两条修复轨迹。

可共享的是确定可复用的检索与观察。不同方案若会改变文件或运行状态，不应把两者的执行结果假装成来自同一环境。

### 4.4 仍有实质分歧时，最多展开两条

第一轮设计参数：最多 2 条分支，每条最多 3 个 Policy 动作，或到达第一个可比较证据点即停止。3 步只是待调参数，不代表足以验证所有方案。限制过早截断或系统性惩罚长方案时应记录并调节。

- 定位分歧：比较哪个探针带来新的区分性证据。
- 修复分歧：从同一个执行状态检查点，分别做最小修改并验证。
- 出现明确矛盾、重复无新增或预算耗尽时停止扩展。
- 只有选中的分支环境和它自己的历史继续执行；兄弟分支结果可作为独立、注明来源的观察提供，不能拼成同一条执行历史。

写操作分支需要隔离的完整环境。Git patch 只能恢复已跟踪代码，不能恢复未跟踪文件、进程、依赖及缓存等状态；若无法保证可比执行状态，第一版只做方案选择，不声称做了执行后反事实比较。

第一阶段可以先上线“语义方案比较、只执行被选一路”，降低改造成本；但这只能检验方向引导，无法充分检验短程执行证据的价值。执行分支应作为独立机制逐步验证。

### 4.5 让策略持续一小段，而非每步重新监督

一次选择可以覆盖最多 3 个动作，遇到新的矛盾证据、测试结果、阶段转换或预算到期即失效。有效期不能屏蔽新的错误证据。常规步骤不重复调用监督器。

默认宽度 2；不因“习惯三选一”强行增加第三条。只有前两条无法覆盖一个独立、有证据支持的方案，且开发集显示有价值时，才研究宽度 3。

## 5. 分支预算与价值判断

理想标准是：额外分支带来的预期最终收益，大于其生成、监督、工具执行、隔离环境和延迟成本。这个量未知，不能把它写成已有精确估计。

第一版用可审计条件判断：有具体方案差异、有错误承诺的后果、有短程可检验结果、没有更便宜的共享探针、预算足够。门控和方案卡成本全部纳入。

可在开发集选择一个额外计算预算上限，例如单轨预测成本的 15% 或 30%，并做敏感性分析。这些是候选参数，不能作为已有结论。实际门控次数、上下文增长及缓存命中不同，按调用回执动态记账，不能只按候选数计算花费。

## 6. 如何确认找到了真正值得分支的节点

### 6.1 离线标注只看当前可用历史

抽样成功和失败任务的前缀，覆盖全部阶段；标注者第一遍不能看到后续成败。记录：事件、当前未决问题、两个可信方案、区分性检查、预期后果、是否有必要执行分支。后续结果可用于第二遍分析，但不能回填成在线可用信号。

仅以已失败任务挑节点，会高估线上门控质量；必须保留成功轨迹和普通推进节点。

### 6.2 用配对干预验证节点价值

从同一可复现状态比较：继续单轨、共享探针、两路短程比较。使用配对种子和相同下游预算，并做若干重复，避免把偶然采样差异当成节点价值。正式判分只用于事后评估，不向运行中的门控暴露隐藏测试。

节点的最终成功率差与成本差才是主要结果；发现新证据、排除一个假设、减少回滚是辅助指标。单次探针成功、补丁变小或分支文本不同，不等于最终任务收益。

### 6.3 验证“选点”而非只验证“多花计算”

建议先在 6–8 个开发任务上做预算和状态恢复检查，再固定规则，用新的 30 个正式任务试验。30 题仅能作为可行性试验，报告配对结果和区间，不据此宣称稳定小幅提升。

推荐核心对照：

1. 单轨 Pass@1。
2. 随机或固定间隔节点分支，匹配额外分支次数、宽度、深度，并尽量匹配真实成本。
3. 事件门控 + 不同假设的方案选择，仅执行一路。
4. 同样门控 + 两路短程执行证据比较。

现有固定三候选 B 可作为历史参考；正式比较需冻结实现版本并保持任务、预算一致。与随机节点比较时，应控制阶段分布，防止随机组被大量等待/收尾节点稀释，制造虚假的门控优势。

## 7. 与文献的关系

- JevCoder：固定问题的概率读数驱动动作类型引导与收尾控制；同模型判断也已有对照。参考：https://arxiv.org/html/2610.19596v1 。
- SWE-Verifier：先评分一个初始动作，再决定是否追加候选；门控思想已有直接先例。参考：https://arxiv.org/html/2610.30284v1 。
- SWE-Search：已有软件工程轨迹树搜索、执行反馈与回溯机制，不能把“短程执行分支”笼统宣称为首次提出。参考：https://arxiv.org/html/2410.20285v6 。
- SWE-Adept：包含基于检查点的替代方案探索和失败修改回滚。参考：https://arxiv.org/abs/2603.01327 。

本方案的待验证重点是：能否以低监督成本找到具有具体假设分歧、可通过短程证据判别的节点，并在真实 API 成本约束下优于等预算的随机扩展和动作评分门控。不能预先声称新颖性或性能收益。
